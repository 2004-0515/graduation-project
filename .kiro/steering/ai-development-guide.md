# AI 辅助开发指南

本规范指导如何在项目开发中高效使用 AI 工具（如 Kiro）。

## 1. 需求分析阶段

### 1.1 需求澄清
当用户提出模糊需求时，AI 应该：
- 主动询问关键细节
- 列出可能的实现方案
- 确认边界条件和异常情况

**示例对话**：
```
用户: "加个优惠券功能"
AI应该问:
- 优惠券类型？（满减/折扣/无门槛）
- 使用限制？（每人限领几张、有效期）
- 与现有订单系统如何集成？
```

### 1.2 需求文档化
复杂功能应创建 Spec 文件：
```
.kiro/specs/
├── feature-name/
│   ├── requirements.md    # 需求和用户故事
│   ├── design.md          # 技术设计
│   └── tasks.md           # 实现任务清单
```

## 2. 设计阶段

### 2.1 数据库设计原则
- 表名使用 `tb_` 前缀（如 `tb_order`）
- 字段使用下划线命名（如 `order_status`）
- 必须包含 `created_time` 和 `updated_time`
- 状态字段使用 TINYINT，定义在常量类中

### 2.2 API 设计原则
- RESTful 风格
- 统一响应格式（见 api-conventions.md）
- 分页参数统一（page/size/sort）

### 2.3 前后端协作
新增功能时必须同步：
1. 后端常量类
2. 前端常量文件 (`constants/index.ts`)
3. 前端类型定义 (`types/index.ts`)
4. API 接口文档

## 3. 编码阶段

### 3.1 代码生成原则
AI 生成代码时应遵循：
- **最小化原则**: 只生成必要的代码
- **一致性原则**: 与现有代码风格保持一致
- **可测试原则**: 生成的代码应易于测试

### 3.2 上下文提供
为 AI 提供足够上下文：
```
# 引用相关文件
#File backend/src/main/java/com/shopping/entity/Order.java
#File frontend/src/types/index.ts

# 或引用整个代码库
#Codebase
```

### 3.3 分步实现
复杂功能分步实现：
1. 先实现数据库表和实体类
2. 再实现 Repository 和 Service
3. 然后实现 Controller 和 API
4. 最后实现前端页面

### 3.4 代码审查要点
AI 生成代码后检查：
- [ ] 是否使用了常量类（禁止魔法数字）
- [ ] 是否有适当的错误处理
- [ ] 是否有必要的日志记录
- [ ] 是否符合项目命名规范

## 4. 调试阶段

### 4.1 错误分析流程
1. 复制完整错误信息给 AI
2. 提供相关代码上下文
3. 说明期望行为和实际行为

### 4.2 常见问题排查
| 问题类型 | 排查方向 |
|----------|----------|
| 编译错误 | 检查类型定义、导入语句 |
| 运行时错误 | 检查空指针、数组越界 |
| 数据异常 | 执行数据完整性检查 |
| 状态显示"未知" | 检查常量映射是否完整 |

### 4.3 使用诊断工具
```
# 查看当前文件的问题
#Problems

# 查看终端输出
#Terminal

# 查看 Git 变更
#Git Diff
```

## 5. 测试阶段

### 5.1 测试覆盖要求
- 后端 Service 层必须有单元测试
- 前端 Store 必须有单元测试
- 关键业务流程需要集成测试

### 5.2 测试命令
```bash
# 后端测试
cd backend && mvn test

# 前端测试
cd frontend && npm run test -- --run
```

### 5.3 数据完整性测试
每次数据变更后执行：
```sql
-- 在 Navicat 中执行
source data_integrity_summary.sql
```

## 7. AI 交互最佳实践

### 7.1 有效的提问方式

**好的提问**：
```
"订单状态显示'未知'，数据库中 order_status=5，
请检查前后端的状态映射是否完整"
```

**差的提问**：
```
"订单有问题"
```

### 7.2 迭代改进
- 第一次输出可能不完美，通过反馈迭代
- 明确指出哪里需要修改
- 提供具体的修改方向

### 7.3 验证 AI 输出
AI 生成代码后必须：
1. 阅读理解代码逻辑
2. 运行测试验证功能
3. 检查是否符合项目规范

## 8. 禁止事项

### 8.1 SQL 执行限制
**禁止**通过 PowerShell 执行包含中文的 SQL 文件：
```bash
# ❌ 错误 - 会导致编码损坏
mysql -u root -p < fix_chinese.sql
```

**正确做法**：在 Navicat 中手动执行（UTF-8 编码）

### 8.2 硬编码禁止
**禁止**在代码中硬编码状态值：
```java
// ❌ 错误
if (order.getStatus() == 1) { ... }

// ✅ 正确
if (order.getStatus() == OrderConstants.OrderStatus.PENDING_SHIPMENT) { ... }
```

### 8.3 直接修改生产数据
**禁止**未经测试直接修改生产数据：
1. 先在测试环境验证 SQL
2. 备份数据
3. 执行修改
4. 验证结果

### 8.4 破坏现有功能
**禁止**任何导致现有功能不可用的修改：

**核心原则**：修改代码时必须确保功能正常运行

**安全问题处理方式**：
1. 在安全审计报告中记录问题和风险
2. 添加注释提醒（如生产环境注意事项）
3. **不要删除**影响功能的配置（如 API 密钥、数据库连接等）

**示例 - API 密钥处理**：
```bash
# ❌ 错误 - 直接删除密钥导致功能不可用
# VITE_AI_API_KEY=your-key-here

# ✅ 正确 - 保留密钥并添加安全提示
# 注意：生产环境应通过环境变量注入，不要提交到公开仓库
VITE_AI_API_KEY=sk-xxx
```

**修改前必须考虑**：
- 这个修改会影响哪些功能？
- 修改后功能还能正常使用吗？
- 如果是安全问题，能否通过添加注释而非删除来解决？
