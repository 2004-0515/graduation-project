# 第三章 系统分析

本章从技术、经济和社会三个维度对系统的可行性进行分析，论证系统开发的合理性和必要性。

## 3.1 可行性分析

### 3.1.1 技术可行性

从技术实现角度来看，本系统的开发具有充分的可行性。首先，系统采用的Java和Spring Boot技术栈已经非常成熟，拥有完善的文档和庞大的开发者社区支持，能够快速解决开发过程中遇到的技术问题。Spring Boot框架提供了丰富的starter依赖和自动配置机制，大幅降低了开发难度和学习成本。

在前端技术方面，Vue框架以其渐进式的设计理念和友好的学习曲线，使得开发者能够快速上手并构建出高质量的用户界面。TypeScript的静态类型检查能够在开发阶段发现潜在问题，提高了代码质量。Element Plus组件库提供了丰富的UI组件，避免了从零开始构建基础组件的工作量。

数据持久化方面，MySQL作为世界上最流行的开源关系型数据库，具有稳定可靠的性能表现。Spring Data JPA的对象关系映射机制简化了数据库操作，使开发者能够专注于业务逻辑的实现。系统采用的前后端分离架构和RESTful API设计已经成为业界标准，技术方案成熟可靠。

在安全性方面，JWT认证机制和BCrypt密码加密算法都是经过广泛验证的成熟技术，能够有效保障系统的安全性。开发团队具备相关技术的使用经验，能够顺利完成系统的开发和部署。综合来看，系统在技术实现上不存在重大障碍，技术可行性良好。

### 3.1.2 经济可行性

从经济投入角度分析，本系统的开发成本较低，具有良好的经济可行性。系统采用的所有核心技术均为开源免费的解决方案，包括Java语言、Spring Boot框架、Vue框架、MySQL数据库等，无需支付任何软件许可费用。开发工具方面，可以使用免费的集成开发环境如IntelliJ IDEA社区版、Visual Studio Code等，进一步降低了开发成本。

系统的部署和运行成本同样较低。对于学习和演示用途，可以在个人计算机上运行，无需购买专门的服务器设备。如果需要正式部署，也可以选择成本较低的云服务器方案，按需付费，避免了大量的前期硬件投资。系统采用的轻量级架构设计，对硬件资源的要求不高，能够在普通配置的服务器上稳定运行。

从开发周期来看，借助成熟的开发框架和组件库，系统的开发效率较高，能够在较短时间内完成核心功能的实现。这意味着人力成本投入相对较少，进一步提升了项目的经济可行性。同时，系统的维护成本也较低，得益于清晰的代码结构和完善的文档，后期的功能扩展和问题修复都能够高效完成。

### 3.1.3 社会可行性

从社会效益角度来看，本系统的开发具有积极的现实意义。随着电子商务的快速发展，网络购物已经成为人们日常生活的重要组成部分。然而，过度消费和冲动购物等问题也日益凸显，给消费者带来了经济压力和心理负担。本系统通过引入理性消费功能，如心愿单冷静期、消费预算管理、价格历史追踪等特色功能，帮助用户建立健康的消费习惯，具有良好的社会价值。

系统的用户界面设计简洁友好，操作流程符合用户的使用习惯，降低了学习成本，使不同年龄段和技术水平的用户都能够轻松使用。系统提供的商品搜索、分类浏览、购物车管理、订单跟踪等功能，能够有效提升用户的购物体验，满足用户的实际需求。

从商家角度来看，系统提供了商品管理、订单处理、销售统计等功能，帮助商家高效管理业务，降低运营成本。管理员后台提供的数据统计和分析功能，能够帮助平台运营者更好地了解业务状况，做出科学的决策。

此外，本系统作为一个完整的电商平台案例，对于学习和研究电子商务系统的开发具有重要的参考价值。系统采用的技术栈和架构设计都是业界主流方案，代码结构清晰，文档完善，能够为其他开发者提供学习和借鉴的范例。综合来看，系统的开发和应用具有良好的社会可行性。

## 3.2 需求分析

### 3.2.1 系统场景描述

本系统面向网络购物场景，为用户、商家和平台管理员提供完整的电子商务解决方案。在典型的使用场景中，普通用户可以通过系统浏览商品、搜索感兴趣的商品、查看商品详情和评价，将心仪的商品加入购物车或心愿单，使用优惠券下单购买，跟踪订单状态，收货后进行评价。系统还为用户提供了理性消费辅助功能，包括设置月度消费预算、查看消费报告、设置商品降价提醒、查看价格历史趋势等，帮助用户做出更加理性的购物决策。

商家用户可以通过系统发布和管理自己的商品，设置商品价格和库存，查看和处理买家订单，进行发货操作，查看销售数据统计。平台管理员负责整个系统的运营管理，包括审核商家发布的商品和上传的图片，管理用户账户，处理订单纠纷，发布和管理优惠券，查看平台整体的运营数据，发送系统通知等。

系统支持多种业务流程。在商品浏览流程中，用户可以按分类浏览商品，使用关键词搜索商品，查看热门商品推荐，查看商品的详细信息、价格历史和用户评价。在购物流程中，用户将商品加入购物车，选择收货地址，选择可用的优惠券，确认订单信息后提交订单，完成支付，等待商家发货，确认收货后可以对商品进行评价。在理性消费流程中，用户可以将暂时不确定是否购买的商品加入心愿单，经过冷静期后再决定是否购买，设置商品的降价提醒，当价格达到预期时收到通知，查看自己的消费统计和预算使用情况。

### 3.2.2 功能分析

系统的功能模块可以分为用户功能、商家功能和管理员功能三大类。

用户功能模块是系统的核心部分，包括用户认证、商品浏览、购物车管理、订单管理、理性消费辅助等功能。用户认证功能支持用户注册、登录、修改个人信息和修改密码。商品浏览功能允许用户按分类浏览商品、搜索商品、查看商品详情、查看商品评价和价格历史。购物车管理功能支持添加商品到购物车、修改商品数量、删除商品和清空购物车。订单管理功能包括创建订单、选择收货地址、使用优惠券、支付订单、取消订单、确认收货和评价商品。理性消费辅助功能包括心愿单管理、消费预算设置、消费报告查看、价格提醒设置和价格历史查看。此外，系统还提供了优惠券领取、收货地址管理、系统通知查看等辅助功能。

商家功能模块为商家提供了商品管理和订单处理的能力。商品管理功能支持商家发布新商品、编辑商品信息、上下架商品、查看商品审核状态。订单处理功能允许商家查看待发货订单、处理订单发货、查看订单详情、查看销售统计数据。商家发布的商品需要经过平台管理员审核后才能上架销售，确保商品信息的真实性和合规性。

管理员功能模块提供了平台运营管理的全面支持。用户管理功能支持查看用户列表、启用或禁用用户账户、查看用户详细信息。商品管理功能包括查看所有商品、审核待审核商品、编辑商品信息、删除违规商品。订单管理功能允许管理员查看所有订单、处理订单纠纷、查看订单统计数据。分类管理功能支持添加、编辑和删除商品分类。优惠券管理功能包括创建优惠券、设置优惠券规则、启用或禁用优惠券、查看优惠券使用情况。文件审核功能用于审核用户上传的图片，防止违规内容。通知管理功能支持发送系统通知、促销通知等。数据统计功能提供平台整体的运营数据分析，包括用户数量、商品数量、订单数量、销售额等关键指标。

### 3.2.3 角色分析

系统定义了三种用户角色，分别是普通用户、商家用户和管理员，每种角色具有不同的权限和功能访问范围。

普通用户是系统的主要使用者，代表了购物平台的消费者群体。普通用户可以浏览和搜索商品，查看商品详情和评价，将商品加入购物车或心愿单，创建订单并完成支付，跟踪订单状态并确认收货，对购买的商品进行评价，领取和使用优惠券，管理收货地址，设置消费预算和查看消费报告，设置商品降价提醒，查看系统通知。普通用户无法访问商品管理和平台管理功能，只能对自己的数据进行操作。

商家用户代表了在平台上销售商品的商户。商家用户除了拥有普通用户的所有权限外，还具有商品管理和订单处理的权限。商家可以发布新商品并上传商品图片，编辑自己发布的商品信息，查看商品的审核状态，查看买家的订单并进行发货操作，查看自己的销售数据统计。商家发布的商品需要经过管理员审核后才能在平台上展示和销售。商家只能管理自己发布的商品和处理自己的订单，无法访问其他商家的数据和平台管理功能。

管理员是系统的最高权限角色，负责整个平台的运营管理。管理员拥有系统的所有功能权限，包括用户管理、商品审核、订单管理、分类管理、优惠券管理、文件审核、通知管理和数据统计等。管理员可以查看和管理所有用户的信息，审核商家提交的商品和图片，处理订单纠纷和异常情况，管理商品分类和优惠券，发送系统通知，查看平台的整体运营数据。管理员发布的商品和上传的文件无需审核，自动通过。管理员的操作会被系统记录，确保平台运营的规范性和可追溯性。

三种角色之间存在明确的权限边界和协作关系。普通用户通过购买商品与商家产生交易关系，商家通过发布商品为用户提供商品选择，管理员通过审核和管理确保平台的正常运营。这种角色划分既保证了系统的安全性，又满足了不同用户群体的功能需求。

## 本章小结

本章从可行性和需求两个方面对系统进行了全面分析。可行性分析从技术、经济和社会三个维度论证了系统开发的合理性，表明系统在技术实现、成本投入和社会效益方面都具有充分的可行性。需求分析部分描述了系统的应用场景，详细分析了用户功能、商家功能和管理员功能三大功能模块，明确了普通用户、商家用户和管理员三种角色的权限和职责。通过系统的分析，为后续的系统设计和实现提供了清晰的需求依据和功能规划。

## 3.3 系统用例建模

### 3.3.1 系统用例图

系统的主要参与者包括普通用户、卖家用户和管理员三类角色。普通用户可以浏览商品、搜索商品、管理购物车、下单购买、管理订单、使用理性消费功能等。卖家用户除了拥有普通用户的功能外，还可以发布商品、管理商品、处理订单、查看销售数据等。管理员拥有最高权限，可以管理用户、审核商品、管理订单、查看统计数据、管理系统配置等。

核心用例包括用户注册登录、商品浏览搜索、购物车管理、订单处理、商品管理、理性消费管理、系统管理等。这些用例之间存在包含和扩展关系，例如下单购买用例包含选择收货地址和选择支付方式等子用例，订单处理用例可以扩展为取消订单、申请退款等特殊场景。

### 3.3.2 系统用例规约

以"用户下单购买"用例为例进行详细说明。该用例的主要参与者是已登录的普通用户，前置条件是用户已登录且购物车中有商品。基本流程包括：用户进入购物车页面，选择要购买的商品，点击结算按钮，选择或新增收货地址，选择可用的优惠券，确认订单信息，选择支付方式，完成支付，系统生成订单并扣减库存。后置条件是订单创建成功，库存更新，用户可以在订单列表中查看订单详情。

扩展流程包括多种异常情况的处理。如果商品库存不足，系统提示用户并阻止下单。如果用户未设置收货地址，系统引导用户添加地址。如果支付失败，订单状态保持为待支付，用户可以重新支付。如果用户在待支付状态下取消订单，系统恢复商品库存。

以"卖家发布商品"用例为例说明卖家功能。该用例的主要参与者是已登录的卖家用户，前置条件是用户具有卖家权限。基本流程包括：卖家进入商品管理页面，点击发布商品按钮，填写商品信息（名称、价格、库存、描述等），上传商品图片，选择商品分类，提交审核。如果是管理员发布商品，则自动审核通过并上架；如果是普通卖家，则需要等待管理员审核。后置条件是商品信息保存成功，等待审核或已上架。

以"管理员审核商品"用例为例说明管理功能。该用例的主要参与者是管理员，前置条件是存在待审核的商品。基本流程包括：管理员进入商品审核页面，查看待审核商品列表，点击查看商品详情，审核商品信息和图片，选择通过或拒绝，填写审核意见（拒绝时必填），提交审核结果。后置条件是商品审核状态更新，卖家收到审核通知。

## 3.4 系统主要类模型

系统的核心领域模型包括用户、商品、订单、购物车等实体类，以及它们之间的关联关系。

用户类（User）是系统的核心实体之一，包含用户名、密码、角色、状态等基本属性。用户与订单、购物车、评价、心愿单等实体存在一对多的关联关系。用户类通过角色属性区分普通用户、卖家和管理员，不同角色拥有不同的操作权限。

商品类（Product）包含商品名称、价格、库存、描述、分类、卖家等属性。商品与分类存在多对一关系，与卖家（用户）存在多对一关系。商品可以被添加到购物车，可以被下单购买，可以被用户评价，可以被添加到心愿单。商品类还包含审核状态和上架状态等管理属性。

订单类（Order）包含订单号、用户、总金额、支付金额、订单状态、支付状态等属性。订单与用户存在多对一关系，与订单项存在一对多关系。订单类封装了订单的完整生命周期，包括创建、支付、发货、收货、评价等状态转换。

订单项类（OrderItem）表示订单中的具体商品，包含商品信息、数量、价格、卖家等属性。订单项与订单存在多对一关系，与商品存在多对一关系。订单项记录了购买时的商品快照信息，避免商品信息变更对历史订单的影响。

购物车类（Cart）表示用户的购物车项，包含用户、商品、数量等属性。购物车与用户存在多对一关系，与商品存在多对一关系。购物车数据持久化存储，支持用户跨会话访问。

分类类（Category）表示商品分类，包含分类名称、图标等属性。分类与商品存在一对多关系，支持商品的分类管理和筛选。

评价类（Review）表示用户对商品的评价，包含用户、商品、订单、评分、内容等属性。评价与用户、商品、订单都存在多对一关系。评价功能帮助其他用户了解商品质量，为购买决策提供参考。

心愿单类（Wishlist）是理性消费功能的核心实体，包含用户、商品、添加时间、冷静期状态等属性。心愿单与用户、商品存在多对一关系。心愿单通过设置冷静期，帮助用户避免冲动消费。

价格历史类（PriceHistory）记录商品的价格变动，包含商品、价格、记录时间等属性。价格历史与商品存在多对一关系，支持用户查看商品的历史价格走势。

价格提醒类（PriceAlert）表示用户设置的降价提醒，包含用户、商品、目标价格、提醒状态等属性。价格提醒与用户、商品存在多对一关系。当商品价格低于目标价格时，系统自动通知用户。

优惠券类（Coupon）表示平台发放的优惠券，包含优惠券类型、折扣值、最低消费、有效期等属性。用户优惠券类（UserCoupon）表示用户领取的优惠券，包含用户、优惠券、领取时间、使用状态等属性，与用户和优惠券都存在多对一关系。

这些核心类通过合理的关联关系构成了系统的领域模型，支撑了系统的各项业务功能。类之间的关系遵循面向对象设计原则，保持了良好的内聚性和低耦合性。
